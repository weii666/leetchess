# leetchess — POC 設計文件

象棋排局（紅先必勝）練習程式。使用者執紅，引擎執黑當陪練。

> **適用範圍：本文件僅涵蓋 `poc/`。**
>
> 服務級的產品定位、技術約束與目錄結構以 `.kiro/steering/` 為準（`product.md`、`tech.md`、`structure.md`、`roadmap.md`）。本文件早於 steering 建立，其中跨越 POC 範圍的決策已被接收至 steering；兩者衝突時**一律以 steering 為準**。
>
> 本文件保留的價值在於兩處尚未被 steering 接收的內容：§2 的已否決方案記錄，以及 §4.3 走脫判定表的展開規則 —— 後者是延後能力的唯一詳細設計來源，屆時實作前需重新檢視。

## 1. 架構定案

**native Pikafish + 後端 API，前端為輕量 client。**

- 黑方應手：伺服器端 native Pikafish **live 計算**，前端經 HTTP 取得
- 紅方走脫判定：**離線預解**成判定表，查表（已依 §6 降為可延後升級）

這個分工是核心。走法由引擎當下算（產品體驗），勝負事實離線算（客觀事實，live 推導不可靠）。

交付形態仍是 **service —— 開頁面就能練，不安裝**。前端不下載任何引擎構件。

> **架構變更（2026-08-08）：** 原定案為「純前端 WASM，無後端，靜態託管」，已推翻。三個理由：
>
> 1. §6 把判定表降為可延後升級後，live 引擎從 fallback 變成**核心**，§2 否決後端的原句理由「唯一需要它的是 fallback 路徑，而 fallback 已被判定表消除」隨之失效。
> 2. Pikafish 官方 release 與 CI **都不產出 wasm 構件**（CI matrix 只有 x86-64、macOS universal、Android arm64），npm 與 GitHub 亦無可信社群 port，只能自建工具鏈。
> 3. 純前端須讓使用者下載 **51MB 的 `pikafish.nnue`**；native 全速跑（WASM 約為 native 的 1/3–1/2）又能把 `go nodes` 開更高，直接改善 §6 自承的「信號未知偏多」。
>
> 已知代價：需要真的伺服器與持續營運成本、離線不可用、每一手都有網路往返。完整決策記錄見 `.kiro/steering/roadmap.md`。
>
> **本次僅同步 §1 與 §2。** §5 的 `web/` 佈局、§6 的資源載入與效能預期、§8 的 GPL 散布義務、§9 的「目前僅有 WASM 實作」**仍以舊架構為前提，尚未同步**，閱讀時請以本節為準。

> **試行中的調整（見 §6）：** 產品先以「純實戰 + 三態諮詢信號」起步 —— **只在真終局停局**，走脫與否用 live 引擎的 mate 分數當諮詢信號（允許「未知」），**不強迫重來**。判定表因此從 v1 的核心降為**可延後升級**：要「就是這一步」的移動級確定回饋時再上。上述離線分工仍是終局形態。這條路成立的前提是 corpus（《適情雅趣》前兩百局這類強制殺局）「紅走脫即被反殺」，真終局本身即給出黑勝——待驗證，見 §3 開工前該驗證的。

## 2. 已否決的方案與理由

寫下來是為了避免重新討論。

| 方案 | 否決理由 |
|---|---|
| 桌面 binary（Tauri/Electron） | 交付形式定為 service，不安裝。**此列仍成立** |
| 純前端 WASM（多執行緒） | 官方 release 與 CI 都不產出 wasm 構件，只能自建；且 Makefile 的 wasm32 分支硬帶 `-pthread`，需 SharedArrayBuffer，連帶要求 COOP/COEP，GitHub Pages 直接出局。自建工具鏈 + 51MB 首載 + 瀏覽器相容性，成本高於後端 |
| 純前端 WASM（單執行緒） | 拿掉 `-pthread` 可消除 COOP/COEP 全部麻煩、任何靜態託管皆可用，營運成本為零，此路確實可行；但仍需自建 wasm 工具鏈、仍要下載 51MB nnue，且改 build flag 觸發 GPL v3 改動開源義務。權衡後未採用 |
| Pikafish 作為 git submodule | `.nnue` 不在 repo 內，submodule 只鎖了一半版本卻給人已鎖好的錯覺；且需自行編譯、GPL 邊界模糊 |
| 完整解樹（含黑方走法）查表 | 明確否決。黑方應手必須是引擎當下計算 |
| 只在短局提供走脫判定 | 功能不一致比功能缺席更傷 |

**兩列已從本表移除：**

- **後端 API** —— 原否決理由為「唯一需要它的是 fallback 路徑，而 fallback 已被判定表消除」。§6 把判定表降為可延後升級後，live 引擎成為核心，此理由失效。**後端 API 已於 2026-08-08 成為採用方案**（見 §1）。
- **不做走脫判定（純實戰模式）** —— 原否決理由為「排局訓練最重要的回饋是『就是這一步』，拿掉學習效果傷害過大」。§6 的試行決定實質上就是採用純實戰模式（真終局停局 + 三態諮詢信號），此列與現行設計直接矛盾，故移除。判定表並未取消，只是延後（見 §6）。

## 3. 黑方應手策略（不是 bit 級確定性）

**不要求黑方每次走同一步。** 每次走同一步等於背棋譜，不是學會殺法。排局訓練的價值在**泛化**：面對黑方各種最頑強的抵抗，都能用同一套技術贏下來。

規則：黑方**每次都走在「抵抗最頑強的一檔」**（把殺著距離拖到最長的等價應手），並在**這一檔之內**變化。變化只允許發生在最頑強應手之間——絕不能走出較弱的手，那等於放水，殺法變簡單、訓練失真。

- 取法：MultiPV 取出所有把 DTM 拖到最長的等價應手，在其中挑選（跨次挑戰可換路線）。
- 這與判定表相容且互不干擾：判定表本就展開黑方**所有**合理應手（§4.3），黑方變化照樣命中，「紅方是否仍必勝」依舊瞬間且正確。**產品要變化 ≠ 判定要變化**。

引擎調用條件：

```
setoption name Hash value 128
position fen <fen> moves <...>      # 每次重送完整狀態,引擎 stateless
go nodes <N>                        # 不是 movetime
```

- **`go nodes` 而非 `go movetime`**：這裡的目的不是重現同一步，而是當**品質下限**——保證每次都搜得夠深、確實走在最頑強那一檔，而非負載一變就淺搜走出弱手。
- **引擎完全 stateless**：悔棋/跳步/重來都只是重送一次。
- **`Threads` 可放開**：既然不追求 bit 級一致,多執行緒既提速、又在「等價最佳防守之間」天然產生變化,變化幾乎免費。
- 代價：牆鐘時間浮動（簡單局面 <1s，複雜局面數秒），UI 需非同步 + loading 狀態。

### 單次挑戰內的穩定性

同一次挑戰之內，悔棋後重走要讓黑方走回同一步（session 內 `(fen, moves) → bestmove` memo），否則退一步重走卻換手會很困惑。**跨次重玩才變化**——正好消掉背題目又不干擾單局操作。

### 開工前該驗證的（優先做）

不再是跨指令集 bit 級一致，而是**判定表完整性**：build 時確認每題的判定表確實把黑方**所有**最頑強應手都展開了。因為使用者現在真的會去踩這些分支，任何遺漏都會在使用者面前變成「判定與實際應手對不上」。

## 4. Build-time（`tools/`）

### 4.1 引擎版本鎖定

```
engine/
├── fetch.sh          # 下載 release binary + nnue,驗 checksum
└── ENGINE_VERSION    # pikafish=<版本>  nnue=<sha256>
```

binary 與 nnue 皆 gitignore。**版本鎖在純文字檔，兩者一起驗 checksum。**
引擎版本或 nnue 一換，所有判定表必須重新產生。

### 4.2 題目驗證

每題用長時間搜尋確認「紅先真的必勝」。

古譜排局有相當比例的「紅勝」結論已被現代引擎推翻（實際為和局甚至紅負）。解不出必勝的題目必須剔除或改標註。**這件事在收題階段做，不要等使用者發現照譜走卻贏不了。**

### 4.3 產出判定表

對每題解出「紅方正確路線 + 黑方所有應手」構成的子樹：

- 紅方走**正著** → 展開黑方所有合理應手
- 紅方走**錯著** → **不展開**。只需知道該著法已丟失勝勢

每節點只存布林值（紅方是否仍必勝），不存走法。體積比完整解樹小一個數量級。

設節點上限（例如 50 萬）。超過上限的大型排局（《七星聚會》《蚯蚓降龍》等，主變可上百回合）標記為「無法完整解出」，這類題目關閉走脫判定功能。500 題中預期只有個位數。

### 4.4 `max_dtm`

每題記錄最長殺著距離，供 UI 顯示殺著倒數、以及判斷該題是否可完整解出。

### 4.5 CI 驗證

- 每個 FEN 丟給引擎 `position fen ... ` + `go depth 1`，能吃就是合法
- 循環規則判定與 Pikafish 規則對齊（見第 7 節）

## 5. 資料佈局

```
leetchess/
├── engine/
│   ├── fetch.sh
│   └── ENGINE_VERSION
├── tools/                    # build-time,唯一用到 Pikafish native 的地方
│   ├── solve.py              # 盤面 → 判定表
│   └── verify.py             # 驗證紅勝 + 規則一致性
├── positions/                # 題目 metadata,進 git,人工編輯
│   └── 0001.json
├── books/                    # 判定表,CI 產出,gitignore 或 LFS
│   └── 0001.verdict.json
└── web/                      # 純前端,無後端
```

**`positions/` 與 `books/` 必須分開。** solver 會反覆重跑（換引擎版本、調參數），題目本身不該跟著動。

一題一檔（非單一大 JSON）：git diff 乾淨，新增題目不碰其他檔案，多人編輯不衝突。

### 題目 schema

```json
{
  "id": "0142",
  "fen": "3ak4/4a4/9/9/9/9/9/9/4A4/3AK1r2 w - - 0 1",
  "side_to_move": "red",
  "max_dtm": 15,
  "solvable": true,
  "difficulty": 3,
  "source": "《適情雅趣》第 87 局",
  "tags": ["車兵殘局"]
}
```

500 題 metadata 總量約 150KB，效能非考量點；選擇標準是編輯友善度。

## 6. Runtime（`web/`）

### 走棋流程（試行:純實戰 + 三態信號）

1. 紅方走一步
2. **只在真終局停局**:輪方合法著數 = 0 → 紅勝 / 黑勝（引擎判定,§7）。不提早、不強迫重來。
3. **發引擎搜尋**取黑方應手,順便讀回傳的 mate 分數 → 更新**三態諮詢信號**（下表）。信號僅供參考,不決定停局。
4. 回到 1

> **原案**（保留備忘）:第 2 步查判定表,走脫時強迫重來。改為諮詢信號是因為前兩百局這類強制殺局「紅走脫即被反殺」,真終局本身就會給出黑勝——信號只需在殺勢翻面時提示,無須離線表即可即時反映。判定表留待需要移動級確定回饋時再上（屆時第 2 步恢復查表,與信號並存)。

### 走法格式

UCI 座標，非中文記譜。檔 `a`–`i`（紅方左至右），列 `0`–`9`（紅方底線為 0）。例：炮二平五 = `h2e2`。前端負責雙向轉換。

### 三態諮詢信號（讀引擎 mate 分數）

信號取自 live 引擎回傳（黑方視角），三態、**允許「未知」**——沒把握就說未知，不硬判：

| score（黑方視角） | 信號 | 意義 |
|---|---|---|
| `mate -N` | **即將紅勝** | 紅方保持殺勢，殺著倒數 = N |
| `mate +N` | **即將黑勝** | 紅方已走成必負，黑方 N 步內殺 |
| `cp X` | **未知中立** | 引擎未搜到殺（**不可據 cp 判走脫** — 排局中 cp 極不可靠），信號誠實地說未知 |

- 信號**會抖 / 未知偏多**:live 定 nodes 逐手浮動，紅方沒走錯也可能在「即將紅勝 ↔ 未知」間跳。諮詢性質可接受;想少一點未知就調高 `go nodes`，代價是每手變慢（與 §3 的品質下限同一旋鈕）。
- 停局**不看信號**，只看真終局（§7），故信號報錯的代價只是一次 UI 抖動，不會誤判勝負。

### 悔棋

砍 `moves` 尾巴重送。配 `(fen, moves) → bestmove` 的 memo cache，退回重走同一步為零成本。

### 資源載入

`pikafish.wasm` + `.nnue` 數十 MB，快取至 IndexedDB，避免每次重抓。首次載入需進度提示。

### 效能預期

WASM 約為 native 的 1/3–1/2。300 萬 nodes 在殘局約 1–3 秒，可接受。

## 7. 兩個會咬人的點

### 循環規則

長將、長捉、一將一殺在排局中是**核心機制**，不是邊緣情況——大量排局的正解建立在「這步是長捉所以黑方必須變著」上，黑方也大量用它謀和。

- 判定表產生時必須完整實作並與 Pikafish 規則書對齊
- 好處：**只需對齊一次**，錯了在 build time 由 CI 抓到，不會讓使用者下到一半發現判定不一致

### 勝負判定

**不要自己實作。**以引擎回傳（`bestmove (none)`、mate 分數）為唯一真相來源，前端只負責顯示。這會省掉最痛苦的一類 bug。

## 9. 抽象介面

引擎存取一律經過單一介面，實作可抽換：

```
EngineAdapter.best_move(fen, moves, nodes) -> (uci_move, score)
```

目前僅有 WASM 實作。若日後需要後端（例如蒐集「使用者在哪一步走脫」的資料以排序題目難度），換掉這一個檔案即可。
