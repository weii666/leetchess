# Implementation Plan

> 本計畫的排序原則:服務端先把「輸入不可能傷害引擎」與「候選題目合不合格由誰說了算」兩件事定下來,前端才開始疊。純函式與平台包裝彼此獨立,可並行;寫入流程本質上是整合,不可並行。

## 1. 收題頁的最小容器

- [ ] 1. 收題頁的最小容器
- [x] 1.1 建立收題頁目錄與最小容器
  - 建立收題頁目錄與最小 HTML 容器,使其可由網址取得
  - 產品的題庫列表頁與對局頁**不加任何連結、按鈕或其他入口**
  - 收題頁的檔案集中於單一目錄,與產品頁面互不牽動;既有的靜態檔掛載規則不變
  - 完成狀態:以網址取得收題頁回 200;既有的題庫列表頁、對局頁與四個既有端點行為皆不變
  - _Requirements: 1.1, 1.3_

## 2. 服務端的權威驗證與輸入把關

- [x] 2.1 (P) 題目 schema 驗證的公開入口
  - 在題庫模組上開一個公開函式,驗證單一候選題目是否符合題目 schema,不合格時以既有的錯誤型別表達
  - 該函式是既有私有驗證的**薄包裝**,不複製也不擴充任何規則;題庫模組的唯讀契約維持不變
  - 完成狀態:對缺欄位、含未知欄位、型別不符的候選題目各得到可辨識的錯誤,且與題庫載入對同一份資料的判定一致
  - _Requirements: 4.7_
  - _Boundary: service/positions.py_

- [x] 2.2 (P) 送往引擎的 FEN 字元把關
  - 在請求模型上新增驗證端點的請求形狀,並對其中的 FEN 施加**字元集白名單與長度上限**
  - 沿用既有著法格式驗證的形狀與錯誤類別,使不合格的請求**在路由函式被呼叫之前**就被擋下
  - 允許的是 FEN 表示法會用到的字元;**任何控制字元一律不在集合內** —— 引擎協定行導向,換行會讓一行指令變成兩行
  - **刻意不做 FEN 文法驗證**:局面合法性由引擎判定,本層只保證字串不會跳出這一行指令
  - 請求模型**不重新宣告題目欄位** —— schema 的權威在題庫模組,此處只取出 FEN 把關
  - 完成狀態:含換行、歸位字元、tab、空位元組或超長的 FEN 各自被拒並得到既有的格式錯誤類別;**既有題庫中的每一個 FEN 全數通過**
  - _Requirements: 9.1, 9.2, 9.3, 9.4, 9.5_
  - _Boundary: service/models.py_

- [x] 2.3 候選題目的驗證服務
  - 新增與對局服務同層的驗證服務,依序執行兩道檢查:題目 schema,而後向引擎確認該 FEN 可載入
  - schema 未通過時**不借引擎** —— 欄位都不對的題目沒有問到引擎的必要
  - 驗證結果以「未通過項目的清單」表達,每一項可定位到欄位;空清單代表合格
  - **不判斷紅先是否必勝**,不執行長時間搜尋;抵達本服務的 FEN 已通過字元把關,不重做字元檢查
  - 完成狀態:合法 FEN 加齊全欄位得到空清單;引擎載入不進去的 FEN 得到對應項目;schema 未通過的候選題目在引擎替身上可斷言零次借用
  - _Requirements: 4.7, 4.10_
  - _Depends: 2.1_

- [x] 2.4 驗證端點與服務組裝
  - 新增候選題目的驗證端點,接受候選題目、回傳驗證結果;啟動掛鉤建立驗證服務
  - **驗證未通過是「結果」而非「錯誤」**:以成功狀態碼回傳含未通過項目的結果,既有的七種錯誤類別碼不為此擴充
  - 既有錯誤類別碼只用於真正的服務失敗:引擎池滿、搜尋逾時、未預期失敗;FEN 字元不合格是唯一的例外,它在更早的一層以格式錯誤表達
  - 完成狀態:端點對合格與不合格候選題目分別回傳對應結果;引擎池滿時回既有的忙碌錯誤形狀而**非**驗證通過;既有四個端點行為不變
  - _Requirements: 1.3, 4.7, 4.8_
  - _Depends: 2.2, 2.3_

## 3. 前端純函式與平台包裝

> 本組三項互不依賴、各自獨立成檔,且**不依賴第 2 組** —— 它們是純函式與平台包裝,不發任何請求。

- [x] 3.1 (P) 表單淺層檢查與描述建議值
  - 實作表單各欄位的淺層檢查:必填是否填妥、題號是否為正整數、標籤是否至少一個,回傳可定位到欄位的未通過項目清單,順序與表單欄位一致
  - 實作 FEN 的結構檢查(列數、每列格數、走子方欄位),以及由 FEN 取得起手方顯示字樣
  - 實作目標路徑檢查:須為題庫目錄內、須位於書目資料夾內、須為題目檔
  - 實作標籤輸入的切分,以及描述的建議值 —— 局號採**逐字**中文數字,與既有題目的寫法一致
  - 這一層**永遠不是放行判準**:不得複製題庫模組的 schema 規則,權威判定屬第 2 組
  - 完成狀態:對各種缺漏回傳定位到正確欄位的清單;結構不合法的 FEN 被指出;題庫根目錄下的檔案與跳出題庫目錄的路徑皆被擋下;上述皆以在瀏覽器中執行純函式的方式驗證
  - _Requirements: 2.4, 2.6, 3.6, 3.7, 4.1, 4.2, 4.6, 5.1, 5.2, 5.3, 8.4_
  - _Boundary: check.js_

- [x] 3.2 (P) 題目序列化與文字層追加
  - 實作單一題目的序列化,排版與既有題目檔同形:兩格縮排、欄位各自一行、**標籤陣列維持單行**、中文不轉義
  - 序列化**只涵蓋題目 schema 的人工編輯欄位**,不寫出最長殺著距離、出處與起手方
  - 實作追加:讀入目標檔既有全文,定位收尾的收束符號,在其前插入新題文字。**既有內容不重新序列化** —— 輸出以既有全文的每一個位元組為前綴
  - 目標檔內容無法解析為題目陣列時以專屬錯誤表達,不寫入
  - 處理三種形態:檔案不存在(產出單元素陣列)、空陣列(不補逗號)、非空陣列(為前一個元素補逗號)
  - 完成狀態:對**既有題庫檔中的每一題**重新序列化後與原檔對應片段逐字相同;三種形態各有對應輸出;非陣列輸入拋出專屬錯誤;追加後的輸出可驗證為以既有全文為前綴
  - _Requirements: 5.4, 5.5, 5.6, 5.7, 5.8, 5.9, 7.4, 7.5_
  - _Boundary: corpus-file.js_

- [x] 3.3 (P) 檔案系統存取的平台包裝
  - 實作平台能力偵測、題庫目錄授權的取得、相對路徑的讀檔與寫檔
  - 目錄控制代碼**只存在模組層變數**,不做持久化;同一分頁內只詢問一次目錄
  - 讀取不存在的檔案回傳「不存在」而非拋出;寫入回傳時內容已落盤
  - 授權被拒絕或目錄選擇被取消,以及平台不支援,各以可辨識的錯誤表達
  - 授權請求必須可由使用者手勢的呼叫堆疊內觸發
  - 完成狀態:能力偵測在支援與不支援的環境各回傳正確結果;拒絕授權與不支援兩種情況產生**不同**的可辨識錯誤;本模組是收題頁中唯一接觸平台檔案 API 的地方
  - _Requirements: 6.1, 6.2, 6.3_
  - _Boundary: fs.js_

## 4. 收題頁的版面、繪盤與欄位

- [x] 4.1 表單容器與左盤右欄版面
  - 補齊收題頁容器:左側盤面區、右側表單區,表單含題號、局名、描述、難度、標籤、FEN 與目標檔案路徑
  - 描述欄位允許換行;**不提供**最長殺著距離與出處的輸入;**不提供**任何編輯或刪除既有題目的操作
  - 版面沿用既有的 flex 慣例;收題頁的樣式表**須自帶盤面的尺寸規則**,對局頁那組不會套到本頁
  - 平台不支援時的說明訊息有固定位置
  - 完成狀態:頁面呈現左盤右表單兩欄;所有使用者可見文字為繁體中文;DOM 中不存在任何編輯或刪除既有題目的控制項
  - _Requirements: 3.1, 3.4, 3.5, 3.8, 6.3, 7.6, 8.1, 8.2, 8.3_

- [x] 4.2 貼上 FEN 即時繪盤
  - FEN 輸入的每一次變動都重跑結構檢查並重繪盤面,以紅方底線在下的視角呈現
  - 盤面以**空的合法著法集合**繪製,因而整片不可選取 —— 不新增任何唯讀模式參數,不修改既有繪製模組
  - 結構不合法時顯示訊息並**清掉盤面**,不繼續顯示前一個可解析內容的局面;清空輸入時呈現空盤面
  - 依 FEN 的走子方顯示起手方
  - 完成狀態:貼上合法 FEN 後盤面出現對應棋子;點擊盤面任何一格都不產生選中框、落點標示或任何變化;貼上不合法 FEN 後訊息出現且盤面不留前一個局面
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5, 2.6_
  - _Depends: 3.1_

- [x] 4.3 欄位互動、難度選項與檢查結果呈現
  - 難度呈現為三選一,選項自既有的難度說法模組產生,不另寫一份說法
  - 題號與局名皆已填而描述仍為空時,提供可自由改寫的描述建議值;描述的最終值以輸入內容為準
  - 淺層檢查的未通過項目呈現在畫面上並定位到欄位,而不只是停用寫入操作;任一項未通過時寫入操作停用
  - 完成狀態:難度只能三選一且說法與列表頁一致;必填未填時寫入操作停用且畫面指出是哪一項;描述建議值出現後可被覆寫且覆寫值被保留
  - _Requirements: 3.2, 3.3, 3.6, 3.7, 4.1, 4.2, 4.6, 8.3, 8.4_
  - _Depends: 3.1_

## 5. 寫入流程整合

> 本組每一項都跨越收題頁組裝層與其協作者(驗證端點、平台包裝、序列化),屬明確的整合任務。四項共用同一份頁面狀態,**不可並行**。

- [x] 5.1 撞號檢查
  - 寫入前重新取得題庫索引的既有題號,與**本分頁已成功寫入的題號集合**取聯集後比對
  - 兩者皆無該題號時視為撞號檢查通過
  - 已寫入題號**只在寫入成功後才加入**,失敗的嘗試不佔用題號
  - 完成狀態:題號與既有題目重複時擋下並指出重複的題號;同一分頁連續寫入兩題且第二題與第一題撞號時擋下 —— 即使題庫索引尚未更新亦然;題號兩邊皆無時放行
  - _Requirements: 4.3, 4.4, 4.5_
  - _Depends: 2.4, 4.3_

- [x] 5.2 送出權威驗證與失敗歸類
  - 撞號檢查通過後,把候選題目送往驗證端點,取得驗證結果
  - 驗證未通過時呈現未通過項目,與淺層檢查的項目**同形**,呈現層不分辨來源
  - 服務不可用、逾時、網路失敗一律歸為「確認未能完成」並**不執行寫入** —— 不得視為驗證通過
  - 後端失敗分類沿用既有的錯誤類別列舉,不新增第二套分類
  - 完成狀態:驗證端點回忙碌或逾時時不寫入且訊息為確認未能完成;驗證未通過時不寫入且未通過項目定位到欄位
  - _Requirements: 4.7, 4.8, 4.9_
  - _Depends: 2.4_

- [x] 5.3 目錄授權、重讀目標檔與寫回
  - 驗證通過後才請求目錄授權 —— 不合格的題目不讓使用者先跳一次目錄選擇框
  - 授權取得後**才重讀**目標檔,把讀檔到寫檔的視窗壓到最小,再以文字層追加產生新全文並寫回
  - 授權尚未取得時,繪盤與欄位填寫**仍然可用**
  - 平台不支援時明確告知不支援與原因;拒絕授權或取消選擇時保留已填入的全部內容並告知寫入未進行
  - 完成狀態:未授權狀態下仍可貼 FEN 繪盤與填寫全部欄位;拒絕授權後表單內容一字不少;寫入成功後目標檔含新題且既有題目逐字不變
  - _Requirements: 6.1, 6.2, 6.3, 6.4_
  - _Depends: 3.2, 3.3_

- [x] 5.4 寫入結果呈現與連續收題
  - 寫入成功時顯示成功訊息並指明寫入的題號與目標檔案,清空題目欄位但**保留目標檔案路徑**
  - 寫入過程失敗時保留已填入的全部內容並顯示失敗原因;目標檔不是合法題目檔屬此類
  - 題庫索引取得失敗時不另立分支,落在一般寫入失敗處理
  - 寫入期間停用寫入操作,避免重複送出
  - 完成狀態:成功後題目欄位清空而目標檔案路徑仍在,且該題號已進入本分頁的已寫入集合;任一種失敗後表單內容全數保留
  - _Requirements: 7.1, 7.2, 7.3_

## Implementation Notes

- **1.1**:`/editor/` 的網址完全由檔案位置決定,`StaticFiles(html=True)` 直接接手,`service/main.py` 不需要任何改動。既有端點是否仍被路由層接手,可用「方法不符 → 405」探測,不必啟動引擎。
- **2.1**:`difficulty` 的 1/2/3 值域**執行期沒有任何一層強制**(`structure.md` 明載),後端不得補上 —— 補了會連帶改變 `PositionRepository.load()` 的行為。三選一只在前端(3.2 / 任務 4.3)。
- **2.2**:`fen` 缺欄位或非字串時,字元把關**刻意放行**,交由 `validate_position()` 以 schema 的說法回報。已驗證沒有任何路徑能讓非字串抵達引擎:`_read_str()` 與 `_check_fields()` 都在借引擎之前擋下,含 `{"fen": ["a\nquit"]}` 這種 f-string 插值會嵌入換行的形狀。
- **2.2**:`validate_fen(value: str)` 的型別窄於 `validate_move(value: Any)`。目前唯一呼叫端有 `isinstance` 前置檢查所以不可達;**2.3 / 2.4 若新增呼叫端,非字串會走成 500 而非 400**,屆時要麼加 isinstance 要麼放寬簽章。

1. 由真實按鈕觸發取得授權,選 `positions/`,**只跳一次**對話框
2. 再按一次寫入,**不應**再跳對話框
3. 重整後按 Esc 取消對話框 → 出現「未取得題庫目錄的存取授權」且表單內容仍在;再按一次,對話框應該回來
4. 讀不存在的檔案得到「不存在」、讀既有檔案得到原文
5. 寫入後以 `git diff` 確認落盤的位元組
6. 以 Firefox 或 Safari 開啟同一頁,確認出現「不支援」訊息

## 刻意接受的覆蓋缺口

- **分頁第一次寫入時,若權威驗證慢到超過使用者手勢的有效期(實測約 5 秒),目錄選擇框開不起來且畫面不說話。** 觸發條件見 Implementation Notes 的 5.3 條目:需要第一次寫入與引擎池被佔住同時成立,而復原方式是再按一次寫入。為它另立一種錯誤型別要重開 `fs.js` 已關閉的 boundary,代價與機率不成比例。這是**決定,不是遺漏**。

- **平台檔案 API 的實際呼叫不進自動化測試** —— 系統目錄選擇框無法由自動化工具操作。第 6 組以注入替身驗證流程,平台包裝本身的正確性靠能力偵測的分支測試加人工驗收。這是 design 的 Testing Strategy 已載明的決定,不是遺漏。
