# Implementation Plan

## 1. 基礎:專案環境與共用契約

- [x] 1.1 建立 uv 管理的 Python 專案環境
  - 於專案根建立 `pyproject.toml`(鎖 `requires-python`)與 `.python-version`,依賴鎖進 `uv.lock` 並納入版本庫
  - 宣告 FastAPI、Pydantic、uvicorn 與測試框架依賴
  - `.gitignore` 新增 `.venv/`
  - 完成狀態:`uv sync` 可在乾淨環境建立 `.venv`,且 `uv run python -c "import fastapi, pydantic"` 無錯誤結束
  - 此任務為其餘所有任務的前提,不得假設環境已存在

- [x] 1.2 定義領域型別與錯誤模型
  - 建立紅黑雙方、三態信號、引擎評分、最佳著法、對局狀態、題目等領域型別,全部標註型別提示
  - 定義七種錯誤類別的列舉與對應的服務例外型別,每個錯誤類別帶穩定的機器可讀代碼
  - 領域型別集中於單一模組,使題庫與對局服務共用而不互相依賴
  - 完成狀態:錯誤類別列舉涵蓋設計所列全部七項,且題庫型別與對局型別皆可匯入而不產生循環匯入
  - _Requirements: 5.1_

- [ ] 1.3 建立設定模組與時間預算約束
  - 提供池容量、借用等待上限、搜尋逾時、stop 寬限期、總時間預算、搜尋節點數、題庫路徑等設定項
  - 啟動時檢查三項分項逾時之和不超過總時間預算,不符即拒絕啟動
  - 池容量的預設值先留待 2.3 的實測結果填入,此任務只建立設定機制
  - 完成狀態:以刻意矛盾的逾時組合啟動時,服務拒絕啟動並指出總預算被超出
  - _Requirements: 3.3, 4.1_

## 2. 引擎層:協定封裝與資源池

- [ ] 2.1 實作引擎進程的 UCI 封裝與逾時讀取
  - 啟動單一引擎子進程並完成握手,固定單執行緒與 128MB 雜湊表設定
  - 移植 POC 已驗證的指令序列與輸出解析:合法著法查詢、應手查詢、mate 與 cp 分數解析
  - **所有讀取都必須有逾時上界** —— POC 阻塞於管線讀取且無逾時,引擎不輸出即執行緒永久卡死,此為本任務要解掉的核心技術債
  - **引擎執行檔路徑須可由設定注入**,使測試能以替身進程取代真實引擎 —— 5.5 的逾時與崩潰測試需要能放入永不輸出或主動終止的替身,若路徑寫死則那些測試無法進行
  - 合法著法與勝負判定全部取自引擎輸出,本層不實作任何規則邏輯,循環規則局面亦然 —— 這是判定與所執行引擎保持一致的保證方式
  - 提供進程健康判定與終止操作
  - 完成狀態:以永不輸出的替身進程呼叫任一查詢,方法在逾時後回傳或拋錯,不會無限期阻塞
  - _Requirements: 1.1, 1.4, 1.6, 4.1_
  - _Boundary: EngineProcess_

- [ ] 2.2 實作走法序列驗證
  - 送出局面指令後,以顯示指令取回當前局面,由回傳局面的行棋方與回合數推導實際套用的步數
  - 與請求所帶走法數比對,不符即拋出局面不一致錯誤
  - 驗證內建於協定層的兩個查詢方法之中,不交由呼叫方負責 —— 呼叫方無從得知引擎忽略了哪一步
  - 回合數推導須涵蓋含吃子的序列;**半回合計數器會因吃子重置,不得用於此判斷**
  - 完成狀態:送入含非法著法的序列時拋出局面不一致錯誤,且**斷言回傳內容不是起始局面的合法著法集合** —— 引擎對非法著法靜默忽略,若驗證失效,失敗表現為回傳錯誤局面的資料而非拋錯
  - _Requirements: 5.3_
  - _Boundary: EngineProcess_

- [ ] 2.3 實測引擎資源佔用並定案池容量預設值
  - 量測單一引擎進程啟動後的常駐記憶體,以及多進程並存時的總量
  - 確認評估網路是否隨進程數線性成長,或由作業系統共享 —— 設計以每進程 128MB 雜湊表加 51MB 網路估算,**此假設尚未驗證**
  - 依實測結果決定池容量的預設值,填回設定模組
  - 完成狀態:記錄單進程與多進程的實際常駐記憶體數值,且設定模組的池容量預設值有實測依據而非估算
  - _Depends: 2.1_
  - _Requirements: 3.1_
  - _Boundary: EngineProcess_

- [ ] 2.4 實作引擎池的借還與併發閘門
  - 維持設定容量的可用引擎,借出與歸還為原子操作,同一進程不同時借給兩個請求
  - 借用附等待上限,逾時未借到即拋出服務忙碌錯誤,**絕不無限期等待**
  - 以情境管理器形式提供借用,確保任何離開路徑都必定歸還或標記待重建
  - 完成狀態:池容量內的並行借用彼此不等待;超出容量的借用在等待上限內拋出服務忙碌錯誤而非阻塞
  - _Depends: 2.3_
  - _Boundary: EnginePool_

- [ ] 2.5 實作逾時處置與崩潰重建
  - 搜尋逾時先送出中止指令進入寬限期,寬限期內取得回應則進程繼續服役,逾期則終止並排入重建
  - 偵測已終止或不健康的進程,於背景重建,重建期間池以其餘容量繼續服務
  - 單一進程的失敗不得影響其他進程或使服務停止
  - 完成狀態:強制終止池中一個進程後,後續請求仍由其餘容量正常回應,且該槽位於背景恢復可用
  - _Requirements: 4.1, 4.2, 4.3, 4.4_
  - _Boundary: EnginePool_

## 3. 服務層:題庫與對局判定

- [ ] 3.1 (P) 實作題庫索引與依編號取題
  - 啟動時遞迴掃描題庫目錄,建立題號到題目的記憶體索引;出處由所在資料夾表達,不是欄位
  - **偵測重複題號並拒絕啟動**,使資料錯誤在部署階段暴露而非執行期
  - 最長殺著距離與可解標記可為空值,不得視為必填 —— 這兩欄由題目驗證工具日後回填
  - 新增題目只需放入檔案,不需修改程式或設定
  - 本任務不觸及引擎,可與整個引擎層並行進行;但**其後的 3.2 依賴本任務**,兩者不可並行
  - 完成狀態:以分書目錄的題庫啟動後可依題號取得任一題;查詢不存在的題號拋出題目不存在錯誤;放入重複題號的檔案時啟動失敗並指出衝突的題號
  - _Depends: 1.2_
  - _Requirements: 6.1, 6.2, 6.3_
  - _Boundary: PositionRepository_

- [ ] 3.2 實作對局狀態判定
  - 由題目起手方與走法數推導當前行棋方
  - **終局判定只依據合法著法數為零**,與任何評分無關;合法著法數為零時該行棋方為負方
  - 尚未達真終局時一律回報對局進行中,不得以任何其他條件宣告結束
  - 完成狀態:對走至真終局的序列回報結束並指出勝方;對中途局面一律回報進行中,即使該局面的引擎評分已顯示殺棋
  - _Depends: 2.4, 3.1_
  - _Requirements: 1.1, 1.2, 1.3, 1.5_
  - _Boundary: GameService_

- [ ] 3.3 實作黑方應手與三態諮詢信號
  - 行棋方為黑時取得引擎應手,並一併回傳走後的完整對局狀態
  - 將引擎評分分類為三態:紅方即將取勝時附殺著倒數步數、黑方即將取勝、未搜得殺著
  - **未搜得殺著時一律回報未知,不得以其他評估數值推斷勝負傾向**
  - 行棋方為紅時拒絕應手請求並指出行棋方不符
  - 完成狀態:紅方走出致勝一手後,同一次應手請求即回傳「黑方無著、對局結束、紅方獲勝」,前端無須另外查詢局面狀態
  - _Requirements: 1.4, 1.5, 2.1, 2.2, 2.3, 2.4_
  - _Boundary: GameService_

## 4. 整合:HTTP 契約與應用組裝

- [ ] 4.1 定義請求回應模型與著法格式驗證
  - 定義三個端點的請求與回應結構,走法序列由請求主體承載而非查詢字串
  - 著法格式驗證在進入服務層之前攔截,不合法即拒絕並指出該著法
  - 完成狀態:送入格式不合法的著法時於進入服務層前即被拒絕,回應指出不合法的著法且未觸及引擎池
  - _Requirements: 5.2_
  - _Boundary: HTTP Routes_

- [ ] 4.2 組裝應用與三個端點
  - 實作題目起始局面、局面查詢、黑方應手三個端點
  - 啟動掛鉤建立題庫索引與引擎池,關閉掛鉤釋放全部引擎進程
  - 路由採同步形式以使用框架的執行緒池;**執行緒池容量須配置為大於引擎池容量**,否則請求會在觸及池之前先被卡住,使服務忙碌的語意與資源實況脫節
  - 完成狀態:服務啟動後三個端點皆可回應;關閉後無殘留的引擎子進程
  - _Depends: 3.2, 3.3, 4.1_
  - _Requirements: 1.1, 1.4, 6.1_
  - _Boundary: HTTP Routes_

- [ ] 4.3 實作全域錯誤處理與錯誤類別映射
  - 將服務層與引擎層拋出的例外映射為對應的錯誤類別與狀態碼
  - 未捕捉的例外一律轉為內部錯誤類別,**回應不得包含內部路徑、堆疊追蹤或引擎原始輸出**
  - 任何失敗路徑都必須確保引擎已歸還或標記待重建,不因例外而洩漏池中資源
  - 完成狀態:製造各類錯誤後,回應皆帶穩定的錯誤類別代碼,且回應內容不含檔案路徑、堆疊或引擎輸出;連續觸發錯誤後池中可用引擎數回復原值
  - _Depends: 4.2_
  - _Requirements: 4.4, 5.1, 5.4_
  - _Boundary: HTTP Routes_

## 5. 驗證:單元、整合與併發

- [ ] 5.1 (P) 協定層單元測試

  - 驗證序列驗證的步數推導,涵蓋含吃子的序列
  - 完成狀態:協定層測試涵蓋合法著法解析、mate 與 cp 兩種評分、序列驗證推導三類情境並全數通過

  - 驗證三態信號分類:mate 負值歸紅方即將取勝並帶倒數、mate 正值歸黑方即將取勝、其餘一律歸未知
  - **驗證終局判定與評分無關**:給定合法著法非空但評分已是殺棋的局面,對局仍須回報進行中
  - 完成狀態:上述三類測試全數通過,其中終局與評分無關的案例明確存在

- [ ] 5.3 (P) 題庫索引單元測試

  - 驗證最長殺著距離與可解標記為空值時仍可正常載入
  - 完成狀態:上述四類測試全數通過,其中重複題號案例確認啟動被拒絕
  - _Requirements: 6.1, 6.2, 6.3_
  - _Boundary: PositionRepository_

- [ ] 5.4 整合測試:完整一局與錯誤路徑
  - 以《適情雅趣》第 21 局自起始局面走至紅勝,驗證停局時機與勝方認定
  - 驗證行棋方不符的應手請求、走不出的走法序列、不存在的題號各自回傳對應錯誤類別
  - 驗證錯誤回應不外洩內部細節
  - 完成狀態:一整局可自起始局面走到紅勝且僅在真終局停局;三類錯誤各自回傳預期的錯誤類別代碼
  - _Depends: 4.3_
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 5.2, 5.3, 5.4, 6.2_

- [ ] 5.5 整合測試:逾時與崩潰恢復
  - 以人為卡住的引擎替身驗證搜尋逾時觸發、回傳逾時錯誤類別、且該進程進入重建
  - 強制終止池中一個進程,驗證服務持續可用且該槽位於背景恢復
  - 驗證單次失敗後池中可用引擎數回復原值,服務整體維持可用
  - 完成狀態:逾時與崩潰兩條路徑皆可觸發並自動恢復,恢復後池容量回復至設定值
  - _Depends: 4.3_
  - _Requirements: 4.1, 4.2, 4.3, 4.4_

- [ ] 5.6 併發與回應時間驗證
  - 驗證池容量內的並行請求彼此不等待
  - 驗證池容量內的併發下,單次應手請求耗時不超過無併發時的兩倍
  - 驗證超出池容量與等待佇列的請求於等待上限內回傳服務忙碌,而非無限期等待
  - 以回合制節奏模擬 30 名同時對局的使用者,驗證服務維持正常 —— 使用者思考期間不發請求,瞬時並行搜尋數遠低於在線人數
  - 完成狀態:上述四項量測皆達標,且 30 人模擬過程中無服務忙碌以外的錯誤
  - _Depends: 4.3_
  - _Requirements: 3.1, 3.2, 3.3, 3.4_

## Implementation Notes

- 1.1:專案採**非套件模式**(`[tool.uv] package = false`),`service/` 不會被安裝進 `.venv`。`pyproject.toml` 已設 `[tool.pytest.ini_options] pythonpath = ["."]`,測試才能 `import service`;若移除該設定,所有測試會 `ModuleNotFoundError`。
- 1.1:測試傳輸層用 **`httpx2`** 而非 `httpx` —— starlette 1.5.0 已棄用 httpx 1.x 搭配 `TestClient`,用 `httpx` 每次匯入都會發出 `StarletteDeprecationWarning`。
- 1.1:Python 鎖定 **3.12**(uv 自行下載 3.12.13)。系統 python3 為 3.9.6,不支援 design 大量使用的 `str | None`(PEP 604)語法,一律走 `uv run`。
- 1.1:尚無測試檔時裸跑 `uv run pytest` 會以 exit code 5(no tests collected)結束,不可直接當成失敗。
- 1.2:**`Position` 定義在 `service/types.py`,不在 `positions.py`**(經 review 裁決)。任務 3.1 必須 `from service.types import Position`,**不得重新定義** —— 兩份同名型別會讓 `isinstance` 與 Pydantic 轉換靜默失效。design 的 PositionRepository Service Interface 區塊僅示意結構,已補註說明。
- 1.2:`InternalError.__init__` **接受但丟棄** `message` 參數(刻意設計,滿足 5.4)。要保留失敗細節必須 `raise InternalError() from cause`;傳字串是靜默的空操作。
- 1.2:`GameState` 與 `Position` 是**淺層 frozen** —— `list[str]` 欄位仍可變,且兩者 unhashable。後續任務不得將它們用作 dict key 或放入 set。
- 1.2:5.4 目前只在 `InternalError` 層級強制。其餘六種錯誤依設計接受呼叫端訊息(5.2 需指出違規著法)。**真正的 5.4 卡點在任務 4.3 的全域例外處理器** —— 它不得把引擎 stdout 或例外的 `str()` 塞進 503/504 的訊息欄位。
- 1.2:`ServiceError.code` 預設為 `INTERNAL`,新增第八種例外型別時若忘記在 `EXCEPTION_BY_CODE` 註冊,會靜默回報 INTERNAL/500 而非明確失敗。
