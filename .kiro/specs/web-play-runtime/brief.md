# Brief: web-play-runtime

## Problem

`poc/index.html` 已經能下完一整局,但它是為單機驗證寫的:寫死一題、錯誤處理只有把後端回的字串印出來、每次操作都假設後端瞬間回應。要變成真實使用者用的對局介面,缺的不是棋盤而是**互動的完整性** —— 等待狀態、網路失敗的復原、跨題複用。

而且它**接不上正式服務**:它打的是 POC 的舊 API(`GET /api/start`、`GET /api/state?moves=`、`GET /api/black?moves=`),正式服務是 `GET /api/positions/{id}`、`POST /api/state`、`POST /api/black-move`,方法、路徑與欄位命名全都不同。

## Current State

`poc/index.html`(334 行,vanilla JS + SVG)已具備:

- SVG 棋盤繪製、FEN 解析與盤面渲染
- 選子 → 藍點顯示合法落點(合法著由後端 `go perft 1` 給,前端不判規則)
- UCI 轉中文記譜(`uci2cn`,含縱線序號、進退平、同線前後子判別)
- 三態諮詢信號顯示(即將紅勝 / 即將黑勝 / 未知中立)
- 歷史著法列表、重來按鈕、勝負橫幅

**尚未有**:接上正式 API、引擎思考中的等待狀態與可取消、網路失敗的重試與復原、多題切換、行動裝置版面。

## 產品決定:不提供悔棋

**排局練習不給悔棋。走錯就是走錯,要重新開始只能整局重來。**

這是刻意的訓練設計,不是省略。連帶的技術後果值得寫下來,避免日後被「順手」加回去:

- **不需要 `(fen, moves) → bestmove` 的 session memo。** memo 存在的唯一理由是「悔棋後重走同一步要拿到相同應手,否則退一步卻換手會很困惑」。沒有悔棋,同一局面就不會被重複請求,這個問題不存在。
- **「單次挑戰內的應手穩定性」不需要任何人負責。** 黑方仍在最頑強一檔內變化(`tech.md`),但那個變化只會發生在**跨次重玩**之間 —— 而那正是我們要的:消掉背題目。
- 若日後決定加回悔棋,memo 與應手穩定性必須一併回來,否則退一步重走會換手。

**重來(回到題目起始局面)仍然提供** —— 那不是悔棋,是放棄這一次挑戰重新開始。

## Desired Outcome

在瀏覽器中完成一整局練習:載入題目 → 執紅走子 → 後端引擎執黑應手 → 真終局停局判勝負,過程中三態信號即時更新,可重來,網路慢或斷線時使用者清楚知道發生什麼事而不是畫面卡住。

## Approach

從 `poc/index.html` 移植已驗證的棋盤、記譜與信號邏輯,重點補三件 POC 沒處理的事:

1. **接上正式 API** —— 端點、HTTP 方法與欄位命名全部改掉。走法序列走請求主體而非 query string。
2. **非同步與失敗** —— 每一手都是網路往返,引擎思考期間須有明確的等待狀態;逾時、斷線、後端錯誤都要有可復原的處理路徑,不能讓對局卡在不可知狀態。
3. **跨題複用** —— 題目由外部傳入,不再硬編。

停局條件只認真終局(輪方合法著數 = 0),三態信號僅為諮詢、不決定停局 —— 信號報錯的代價只是一次 UI 抖動,不會誤判勝負。

## Scope

- **In**: 棋盤渲染與走子互動、合法著提示、對局狀態機(走法序列、輪方、終局)、真終局停局與勝負顯示、三態諮詢信號、中文記譜、重來、引擎思考中的等待與取消、網路失敗處理、行動裝置可用的版面
- **Out**: **悔棋與應手記憶(產品決定不做,見上)**、後端 API 的實作(屬 engine-service)、跨題導航與進度紀錄(屬 problem-browser)、題目 schema(屬 position-corpus)、判定表與移動級走脫回饋(後續 phase)、`poc/` 的後續維護

## Boundary Candidates

- 後端 API client(請求、逾時、重試、錯誤模型)
- 對局狀態機(走法序列、輪方、終局)
- 棋盤呈現與互動(SVG 棋盤、選子、合法點)
- 輔助呈現(中文記譜、三態信號、歷史著法)

## Out of Boundary

- **不自實作任何象棋規則** —— 合法著與勝負一律來自後端(`tech.md`「勝負判定不自己實作」),尤其不碰循環規則
- 不持有題目資料的定義權,只消費
- 不決定要載入哪一題
- **不做悔棋**,也不做為悔棋而生的應手記憶
- 不實作判定表,但**走脫回饋的來源必須設計成可插拔**:三態信號是目前唯一來源,日後判定表是新增來源而非改寫流程

## Upstream / Downstream

- **Upstream**: engine-service(HTTP API 契約,已實作完成並通過 335 個測試)、position-corpus(FEN 與 metadata)、`poc/index.html`(移植來源)
- **Downstream**: problem-browser(嵌入或導向本 client)、service-deploy-ops(打包發布)、後續 phase 的 verdict-table(接進走脫回饋插槽)

## Existing Spec Touchpoints

- **Extends**: 無
- **Adjacent**: 與 engine-service 共享 HTTP API 契約,契約已於 engine-service 的 design 階段定案並實作完成。與 problem-browser 的邊界在「單題內迴圈 vs 跨題導航」

> **契約使用約束(來自 engine-service design 與實測)**:
>
> - 使用者走完一手紅方著法後,**直接呼叫 `/api/black-move`,不得先呼叫 `/api/state` 確認終局** —— 前者的回應已涵蓋「紅方這一手就將死黑方」的情況(黑方著法為空、局面結束、勝方為紅),而那正是每一題排局的最後一手。每手多一次呼叫會讓通過後端併發閘門的次數加倍,直接壓縮可承載人數。`/api/state` 只用於重建狀態(頁面重整、載入題目)。
> - **`mate_in` 可能為 `0`**(終局那手),不得用 falsy 判斷,否則倒數會被靜默吞掉。
> - **`move` 為 `null` 時 `signal` 仍可能有值**,兩者是獨立欄位。
> - 錯誤回應為 `{code, message}`,類別碼恆為七種之一;但**路由層的 404 / 405 例外**,回框架原生的 `{"detail": ...}`。

## Constraints

- 每一手都有網路往返:引擎搜尋約 0.12s(native,`go nodes 250000`)加 RTT,UI 必須非同步且有等待狀態
- **殺著倒數可能高估 1 步** —— 250k 節點是取得 mate 型別的門檻,精確 DTM 需 1M(4.5 倍成本)。UI 呈現宜為「約 N 步」而非確數
- 走法內部一律 UCI 座標,中文記譜只在顯示層。檔 `a`–`i`(紅方左至右),列 `0`–`9`(紅方底線為 0)
- 後端無 session 狀態,對局狀態完全由前端持有並每次重送 —— 前端是狀態的唯一真相
- 三態信號會抖、未知偏多是預期行為(`product.md`),UI 呈現須讓使用者理解它是諮詢而非判決
- 繁體中文介面
