# Design Document — problem-browser

## Overview

**Purpose**: 讓題庫列表成為產品入口 —— 使用者開啟服務先看到題庫,選一題才進入對局。這是產品從「一個能下棋的頁面」變成 leetcode 式解題網站的一塊。

**Users**: 練習排局的終端使用者。

**Impact**: 目前 `/` 直接是棋盤(`web/index.html`),換題只能手動改 `?id=`。本功能把入口換成列表,棋盤退居子頁。

### Goals

- 開啟服務先看到題庫,點一題進入對局,下完能回來
- 完成標記由使用者自己按,重開瀏覽器仍在
- 列表不打後端 —— 瀏覽題庫不受引擎負載影響

### Non-Goals

- 對局內的任何互動 —— 屬 web-play-runtime
- 題目 schema 與內容 —— 屬 position-corpus
- `solvable` 的判定 —— 屬 corpus-verification,本功能只依它過濾
- **自動偵測解題成功** —— 產品決定不做
- 帳號、雲端同步、跨裝置進度、題目推薦

## Boundary Commitments

### This Spec Owns

- 題庫列表頁的全部內容:呈現、篩選、完成標記
- **完成狀態**:格式、持久化、版本前綴 —— 這是本 spec 唯一擁有的使用者資料
- **題目索引的產出方式**:由題庫檔案彙整成單一份可靜態取得的資料
- 列表與對局之間的導航契約(以題號交接)
- **入口路由的變更**:`/` 由棋盤改為列表

### Out of Boundary

- **對局介面的內部行為** —— `web/` 既有八個模組的邏輯一律不動
- 題目 schema 與題庫檔案內容 —— 唯讀消費
- `solvable` 的判定
- 引擎服務的任何行為
- **判斷使用者是否真的解出題目**

### Allowed Dependencies

- 題目索引(本 spec 產出)
- `web/style.css` 的既有樣式語言(共用視覺,但列表的樣式由本 spec 新增)
- 瀏覽器原生能力:ES modules、`localStorage`、`fetch`(僅取索引)

**必要的跨界改動**(各為明確的整合點,不得夾帶):

1. `web/index.html` → 改名或移位,使 `/` 讓給列表頁
2. `service/main.py` 的掛載段 —— 若路由結構需要調整
3. `web/app.js` → 加入返回列表的途徑(4.3)

**禁止**:引入任何 node 工具鏈、打包器、前端框架(`tech.md`);讓列表呼叫引擎服務。

### Revalidation Triggers

- 題目 schema 欄位變更(索引產出與列表呈現皆依賴它)
- 完成狀態的儲存格式或鍵名變更
- 入口路由或對局頁位址變更 —— web-play-runtime 與日後的分享連結都依賴它
- `solvable` 語意變更

## Architecture

### 路由:列表接管入口

目前 `web/index.html` 掛在 `/`。本功能把入口讓給列表:

```
/                    題庫列表(新)
/play.html?id=<題號>  對局介面(現有的 index.html 改名)
```

**選擇改名而非新增子目錄**,理由是 `web/` 是扁平佈局(`structure.md` 已記),而 `service/main.py` 的 `_WebFiles` 遮蔽只吃 `/api` 前綴 —— 扁平檔案不需要動掛載邏輯,風險最小。

`web-play-runtime` 已把題號設計成由 `?id=` 從外部傳入,**對局介面的程式不需要為此改動**,只有檔名與一個返回連結會變。

### 列表不打後端

題目 metadata 彙整成**單一份靜態索引**,列表只取它。500 題約 150KB,一次載入無壓力。

這使瀏覽題庫完全不受引擎負載影響 —— 引擎池滿的時候列表照樣能開,只有真的進入對局才會碰到後端。

**索引由一個不碰引擎池的端點提供**(`GET /api/catalog`)。

後端啟動時已經掃描 `positions/` 建立 `PositionRepository` 索引,該端點只是把它讀出來 —— **不借引擎、不觸發搜尋**,因此引擎池滿時列表照樣能開(5.2)。

**未採用靜態檔的理由**:靜態檔要靠一個產出工具維護,題庫變更後忘記重跑就會過期,而過期的列表會讓使用者點進一個不存在的題目。端點沒有這個失效模式 —— 新增題目重啟服務即出現,自動滿足 5.3。

代價是列表確實會發一次請求。這不違反 5.2 的意圖:那條要保證的是**不消耗引擎資源**,而非不發任何請求。requirements 的措辭已據此修正。

**這是本 spec 唯一需要在 `service/` 新增行為的地方**,必須是明確的整合任務。

### 完成狀態:一份題號集合

系統不偵測解題成功,所以進度模型就是「哪些題號被使用者按過」。

```
鍵    leetchess:v1:completed
值    數字題號的 JSON 陣列
```

對齊 grind75 實測的做法(它用 `1:completedQuestions` 與 slug 陣列),差別在主鍵是數字 id 而非 slug —— 更省空間,且與題目 schema 的主鍵一致。

**鍵名帶版本前綴**是刻意的:日後格式若要改(例如加入練習次數或時間),舊鍵可辨識而非誤讀。

**解析失敗一律退回「全部未完成」**(3.6)。使用者手動改壞、舊版本殘留、瀏覽器塞了別的東西 —— 任何一種都不該讓列表打不開。

**已完成但不再列出的題號保留在集合中**(3.7):題目可能因為被標為不可解而下架,日後若重新上架,使用者的標記還在。集合是題號的集合,不是列表的鏡像。

## File Structure Plan

### 新增檔案

```
web/
├── list.html        # 列表頁骨架(成為新的 /)
├── list.css         # 列表版面(與 style.css 共用視覺語言)
├── catalog.js       # 題目索引的取得與篩選(純資料,不碰 DOM)
├── progress.js      # 完成狀態的讀寫與版本處理(純函式 + localStorage)
└── list.js          # 列表組裝:呈現、篩選互動、完成標記、進入對局
```

```
tests/
├── test_web_catalog.py    # 索引與篩選(純函式)
├── test_web_progress.py   # 完成狀態的持久化與損毀復原
└── test_web_list.py       # 列表互動:篩選、標記、進入對局、返回
```

### 修改檔案

- `web/index.html` → **改名為 `web/play.html`**,使 `/` 讓給列表。內容不動
- `web/app.js` → **僅加入返回列表的途徑**(4.3),其餘邏輯不動
- `service/main.py` → 僅在路由結構需要時調整掛載;能不動則不動
- 索引產出的落點依「產出時機」的決定而定

### 依賴方向

```
progress / catalog  →  list
```

`catalog.js` 與 `progress.js` 是純資料層,不碰 DOM —— 與 `fen.js` / `notation.js` 同樣可用 `page.evaluate()` 單獨驗證。`list.js` 是唯一碰 DOM 的模組。

### catalog.js

**責任**:列表所需資料的唯一來源。取得索引後在記憶體中篩選,**不因篩選再次取得資料**。

**關鍵約束**:

- **絕不呼叫引擎服務**(5.2)。它只取索引
- **過濾 `solvable` 為 false 的題目**(1.4)。`solvable` 為空值時視為可上架 —— corpus-verification 尚未回填,不能因此讓整個題庫消失
- 多條件為 AND(2.4)

### progress.js

**責任**:完成狀態的唯一寫入處。

**關鍵約束**:

- **鍵名帶版本前綴**,日後格式變更可辨識舊資料
- **解析失敗退回「全部未完成」**(3.6)—— 不得讓損毀的儲存值使列表打不開
- **不再列出的題號保留**(3.7)—— 集合是題號的集合,不是列表的鏡像
- **不自動寫入任何題號**(3.4)—— 只有使用者的切換操作會改變它

### list.js

**關鍵約束**:

- 唯一碰 DOM 的模組
- **完成題數與總題數須可見**(3.5)
- 返回列表時**保留篩選條件與完成標記**(4.4)
- 繁體中文

## Error Handling

| 情境 | 使用者看到 | 可做什麼 |
|---|---|---|
| 索引取不到 | 題庫載入失敗 | 重試 |
| 題庫為空 | 題庫目前沒有題目(1.5) | —— |
| 篩選無結果 | 沒有符合條件的題目(2.5) | 清除條件 |
| 完成狀態損毀 | **不呈現任何錯誤** —— 靜默退回全部未完成(3.6) | 照常使用 |

完成狀態損毀不告知使用者是刻意的:那是本機資料的技術細節,使用者無從處理,而列表本身完全可用。

## Testing Strategy

沿用既有手法:Playwright 的 Python 綁定、`page.route()` 合成 origin 供真實交付檔、純資料層以 `page.evaluate()` 驗證。

### 純資料層

- **篩選**:單條件、多條件 AND、無結果
- **不可解的題目被排除**,且 `solvable` 為空值時仍列出(否則 corpus-verification 完成前題庫是空的)
- **完成狀態**:寫入後可讀回、版本鍵名正確、**損毀的值退回全部未完成而非拋錯**、不再列出的題號不致失敗

### 列表互動

- 列表呈現每題的題號、局名、難度、標籤、出處
- 篩選後只剩符合的題目;無結果時的告知與清除
- **切換完成標記後重新載入頁面,狀態仍在**(3.3)
- 完成題數與總題數可見

### 導航

- **入口是列表不是棋盤**(1.1)—— 這是本功能最外顯的改變
- 點一題進入對局,且**對局載入的是所選的那一題**(4.2)
- 自對局返回列表,**篩選條件與完成標記仍在**(4.4)

### 版面

- 行動裝置直向畫面完整呈現列表,不需橫向捲動(6.1)
- 已完成與未完成在視覺上可區分(6.3)

### 迴歸

- **既有 608 個測試不得退化** —— 特別是 web-play-runtime 的測試會受檔名變更影響,那是本功能唯一會碰到它們的地方
